# Spec Template

Use as `requirements/<FeatureName>/specs/SPEC-<NNN>.md`. This is the format for
implementation-ready feature specs. The spec must be complete enough that an AI
coding agent can implement from it without a follow-up meeting.

```markdown
# SPEC-XXX: <Feature Name>

**Status**: Draft | Review | Approved | In Development | Done
**Discovery source**: <link to discovery doc>
**Decision records**: <links to relevant ADRs>
**Priority**: P0 (launch blocker) | P1 (important) | P2 (nice to have)

## Overview
One paragraph: what this feature does, why it exists, who it serves.

## Clarifications

Structured Q&A captured during Guided Intake or Eng Review and graduated into
the spec so engineers and agents reading the spec see exactly what was
clarified, when, and by whom. New clarifications append to this section; do
not rewrite history.

| Date | OQ ID | Question | Answer | Asked By | Source |
|------|-------|----------|--------|----------|--------|
| YYYY-MM-DD | TF-01 | <question> | <answer> | PM / Eng / Agent | <discovery file or session> |

Clarifications are how vague intake answers ("users", "intuitive", "ASAP")
become precise spec language. If a question stays open, mark its row
`Status: Deferred` and link to the OQ in the discovery file.

## Users & Roles
Which personas interact with this feature and in what capacity.
Reference specific personas by name — do not say "users".

## Acceptance Criteria

Given/When/Then format with testable assertions. Each criterion has two parts:
the human-readable behavior and a precise assertion that maps to a test. QA
validates the behavior; the agent writes tests against the assertion.

- [ ] **Behavior:** Given <context>, when <action>, then <expected outcome>
      **Assertion:** `expect(result.property).toBe(expectedValue)`

The behavior is what the user writes. The assertion is what the AI generates
during spec-writing by reading the codebase and mapping intent to testable
interfaces. The user reviews the assertion for "does this capture what I meant?"
— not for syntax.

## Functional Requirements

Numbered list of specific behaviors. Be explicit about edge cases — agents
implement what is written, not what is meant. If a requirement is ambiguous,
the agent will make an assumption. Make it unambiguous.

1. The system must ...
2. When <edge case>, the system must ...

## State Combination Matrix

**Include this section when the feature introduces conditional UI behavior**
— enable/disable, show/hide, different content or routing based on multiple
state variables. If the feature has no conditional gates, omit this section.

Enumerate every meaningful combination of state variables that drive behavior.
For each combination, state the expected UI outcome. This table is the canonical
reference for boolean logic in implementation — it replaces prose conditions,
which are ambiguous and invite logic errors.

| State A | State B | State C | → UI Behavior |
|---------|---------|---------|---------------|
| true | true | * | <expected outcome> |
| true | false | true | <expected outcome> |
| true | false | false | <expected outcome> |
| false | * | * | <expected outcome> |

Rules:

- Every row must have one unambiguous UI outcome (not "depends").
- Use `*` for "any value" only when the outcome truly does not vary.
- If a combination is impossible, mark it N/A and state why.
- The engineer reviews this table during Eng Review. If a row is wrong, the
  fix is a table edit, not a code debug.

## Contract Definitions

This section defines the interfaces, types, and operation signatures that tests
will assert against. These are the "seams" between components — the points
where a failing test can be written before any implementation exists.

**This section is generated by the AI during spec-writing, not by the user.** The
AI reads the codebase to:

1. Find existing types/interfaces the new feature should conform to
2. Identify naming conventions and architectural patterns in use
3. Propose new interfaces that extend or compose existing ones
4. Ensure contract definitions are consistent with the codebase

**Critical: Contract Definitions must be grounded, not generic.** Every type,
interface, and operation must reference the real codebase: real file paths, real
existing types being extended, real naming conventions. Placeholder names like
`NewFeatureInput` or `SomeService` are NOT ready — replace with real names that
follow the project's conventions.

### Key Types

```typescript
// Extends: <Type> from <real path>
// Pattern: follows <existing pattern> in <real path>
type FeatureSettings = {
  enabled: boolean
  configOption: ConfigEnum
  resourceId?: string
}

// New type — follows naming convention: [Feature]Result
type FeatureResult = {
  id: string
  appliedAt: number
}
```

### Operations

```typescript
// Module: <real path> (new module, follows <existing pattern>)
// Hook/Service: <real path>

interface FeatureOperations {
  getSettings(id: string): FeatureSettings
  updateSettings(id: string, settings: Partial<FeatureSettings>): void
  // Connectivity loss: must queue via <project's sanctioned mechanism>
}
```

### State Transitions (if applicable)

```
Idle → [user enables in settings] → Configured
Configured → [trigger condition] → Active
Active → [completion] → Processing
Processing → [success] → Complete
Processing → [failure / connectivity loss] → Queued
```

**Codebase references:** Every contract must include at least one
`// Extends:`, `// Pattern:`, or `// Module:` comment pointing to a real path.
If you cannot cite a real reference, flag it: `// ⚠️ No existing pattern found
— needs Eng input`.

## Data Model (Draft)
Sketch of entities, fields, types, and relationships. Should align with the
Contract Definitions above — the data model is the persistence shape, the
contracts are the runtime shape.

## Test Specification

This section defines what tests should be written **before** implementation
begins (TDD). Organize by test boundary so the implementing agent knows what
kind of test to write for each requirement.

The goal: an agent reads this section and immediately generates failing test
files. No interpretation, no follow-up questions, no guessing about file paths
or imports.

### Test Environment

```
Unit runner:    <exact command>
Watch mode:     <exact command>
E2E runner:     <exact command>
Native runner:  <exact command, if applicable>
```

The agent runs the test command after writing tests to verify they fail for
the right reason (missing implementation, not broken test setup).

### Test Boundary Map

Categorize every acceptance criterion and functional requirement into exactly
one test boundary. **Include the file path where the test will be created.**
Mark tests that can be written and executed independently of other tests with
`[P]` (parallel). The implementing agent uses these markers to fan out work
across parallel runners or sub-agents.

| Requirement | Test Type | What It Tests | Framework | Test File Path | Parallel |
|-------------|-----------|---------------|-----------|----------------|----------|
| AC-1 | Unit | <description> | <framework> | <real path> | [P] |
| AC-2 | Integration | <description> | <framework> | <real path> | — |
| AC-3 | E2E | <description> | <framework> | <real path> | [P] |
| FR-2 | Unit | <description> | <framework> | <real path> | [P] |

Parallel marker rules:

- `[P]` — test is independent: no shared fixtures, no shared file state, no
  ordering dependency on another test in the table.
- `—` — test depends on something else (sequential setup, shared fixture,
  data-seeded prerequisite). State the dependency in the "What It Tests"
  cell (e.g., "after AC-1 seeds the workspace").

File paths follow the project's conventions. Determine these from the
Codebase Context section.

### Failing Tests (Write First)

For each test boundary, provide **executable test code** that the implementing
agent writes BEFORE any implementation. These are not comment skeletons — they
are real tests with real imports referencing the Contract Definitions and real
assertions. They must fail because the implementation does not exist yet, not
because the test is incomplete.

Provide one code block per test boundary, in the appropriate language and
framework. The only acceptable failure mode is "module not found" or
"function is not defined".

### Failure Mode Tests

Every edge case and error condition gets a corresponding test. These are often
the most valuable tests because they define the boundaries of correct behavior.

| Failure Scenario | Expected Behavior | Test Type | Test File Path |
|------------------|-------------------|-----------|----------------|
| Connectivity loss during save | Queue, retry on reconnect | Unit | <real path> |
| Invalid input values | Throw descriptive error, do not persist | Unit | <real path> |
| Feature disabled mid-session | Graceful degradation | Integration | <real path> |
| External service timeout | Fallback, queue sync | Integration | <real path> |

## Dependencies

What must exist before this feature can be built?

- Other specs that must be implemented first
- External services or APIs required
- Data that must be seeded or migrated

## Edge Cases

Explicit enumeration of non-obvious scenarios. Every edge case listed here MUST
have a corresponding entry in the Failure Mode Tests table. If you can describe
the edge case, you can describe the test for it.

### Branch Enumeration (for conditional/resource-gated logic)

When the feature branches on resource availability or state, enumerate ALL paths
— not just the happy path and one fallback. Missing branches leave stale state
and uncovered code paths.

| Branch | Condition | State Changes | User Sees | Cleanup |
|--------|-----------|---------------|-----------|---------|
| **Available** | Resource exists and available | <state set> | <UI> | — |
| **Exhausted** | Resource exists, none available | <state set> | <UI> | <what resets> |
| **Absent** | Resource does not exist | <state set> | <UI> | <what resets> |
| **Early return** | Function returns before reaching gate | <state risk?> | <UI> | <stale state risk?> |

The "Early return" row is the most commonly missed. If a function returns false
before reaching an eligibility dispatch, the dispatch never fires and previous
state persists.

## Risk Assessment (Engineering Review Lens)

Populated during Step 6 by the AI; validated and amended by the engineer at
Step 8.

### Business Impact
- Does this unblock revenue, reduce churn, or improve competitive position?
- What is the opportunity cost?
- What happens to the business if this ships late or not at all?

### Technical Excellence
- Does this improve or degrade system reliability?
- Are we introducing tech debt? Is it intentional, time-boxed, with a payback plan?
- Does this align with current architectural direction or create a new pattern?

### Team Velocity
- Will this make the team faster or slower over the next 6 months?
- Is the complexity justified by the value delivered?
- Does the team have the expertise to build and maintain it?

### Risk Register

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| <Specific risk> | Low / Med / High | Low / Med / High | <Concrete mitigation> |

Universal risks to evaluate (omit any that genuinely do not apply):

- **Data loss / durability** during connectivity loss, crashes, or partial failure
- **Performance regression** on hot paths, startup, or constrained-device runtime
- **Blast radius** when touching widely-imported modules, shared schemas, or core data flows
- **Untested regression** of existing behavior with no automated safety net
- **Platform/store review** for store submission, OS permissions, entitlements, third-party policies
- **Live customer-facing failure** mid-task in production
- **Rollback story** — feature flag, server toggle, or new release required?

## Out of Scope

What this spec explicitly does NOT cover. This prevents scope creep and tells
agents where to stop. Be specific.

## API Surface (Draft)

Rough endpoints or operations. Should align with Operations in Contract
Definitions. Not a full API spec, but enough for an agent to understand the
interface shape and write integration tests against it.

## Codebase Context

Populated by the AI during spec-writing by reading the project's codebase. This
replaces guesswork with grounded references and is the foundation for the
Contract Definitions and Test Specification above.

The AI reads the codebase to answer:

- What existing files, services, or patterns are relevant?
- What types/interfaces does this feature need to extend or conform to?
- What middleware, utilities, or helpers should be reused?
- What naming conventions does the codebase follow?
- What testing frameworks, patterns, and file conventions are used?
- Where do tests live? What is the file naming convention?
- What test helpers, fixtures, or factories exist?

Format: concrete file paths and pattern descriptions. This is the "show your
work" step.

### Adjacent Code Health

Examine code adjacent to the feature's touch points — not just files being
modified, but files that run alongside them in the same lifecycle. This
surfaces pre-existing fragilities that could interact with the new feature.

Audit adjacent code for:

- Teardown/cleanup paths that lack error isolation (one throw cascades)
- API calls to methods that do not exist on the target interface
- Sequential operations where partial failure leaves inconsistent state
- Event listeners registered without corresponding removal
- Shared utilities with side effects at import time

## Component Reuse Audit

This section inventories existing UI components before any new ones are
designed or built. The AI populates it during Step 6 by reading the codebase's
component hierarchy and cross-referencing it against the feature's designs
(e.g., Figma frames). The goal: prevent the team from rebuilding components
that already exist, and surface design system deviations before they become
tech debt.

### Figma-to-Component Map

For each screen or surface in the designs, map it to the codebase:

| Design Surface | Existing Component | Path | Reuse Strategy |
|----------------|--------------------|------|----------------|
| <screen name> | <component name> | <real path> | Reuse as-is / New variant / Extend / New component |

Reuse strategies:

- **Reuse as-is** — existing component covers the design with no changes
- **New variant** — needs a new prop or visual variant (most common, highest value)
- **Extend** — needs structural changes (new children, layout slots)
- **New component** — nothing in the codebase matches; build from scratch

### Design System Deviations

Flag any design that introduces a pattern not present in the existing component
library. New patterns are not necessarily wrong, but they need a deliberate
decision.

| Deviation | Design Source | Closest Existing Pattern | Decision Needed |
|-----------|---------------|--------------------------|-----------------|
| <new pattern> | <design frame> | <closest existing> | Adopt new / Align to existing / Defer to Design |

### Missing States

List component states the feature requires but the design does not explicitly
cover. Common missing states: loading, empty, error, offline, disabled,
first-time/onboarding, skeleton/placeholder.

| Component | Missing State | Why It's Needed | Suggested Behavior |
|-----------|---------------|-----------------|---------------------|
| <component> | <state> | <triggering scenario> | <proposed handling> |

## Spec Quality Checklist ("unit tests for English")

Run this checklist over the prose of this spec — Functional Requirements,
Acceptance Criteria, Business Rules, Edge Cases, Failure Mode Tests — to catch
ambiguity that turns into agent guesswork. The agent runs this automatically
during Step 6 / Step 8b. Failures must be fixed before the Readiness Gate
passes.

### Requirement Phrasing

- [ ] Every Functional Requirement starts with an explicit subject + verb (e.g., "The system must…", "The user can…"). No passive voice that hides who acts.
- [ ] Every requirement contains exactly one testable assertion. Multi-clause requirements ("X and Y and Z") are split.
- [ ] No vague modifiers ("appropriately", "as needed", "where applicable", "intuitive", "fast", "robust"). Replace with measurable criteria.
- [ ] Every quantity is specified. Avoid "many", "some", "few" — use exact numbers, ranges, or "configurable, default N".
- [ ] Every error condition is named (not "fails gracefully" — "returns `ErrorCode.RATE_LIMITED` and surfaces the retry-after header").
- [ ] Every time-based behavior has a numeric bound (timeout, debounce, TTL). No "eventually", "periodically", or "soon".

### Persona and Role Specificity

- [ ] No mention of "users" or "customers" without naming the specific persona.
- [ ] Every actor in an Acceptance Criterion is a defined persona from `discovery/00-personas.md`.
- [ ] Multi-persona behaviors are split per persona (the spec describes what each persona experiences differently).

### Coverage and Consistency

- [ ] Every Acceptance Criterion appears in the Test Boundary Map.
- [ ] Every Functional Requirement maps to at least one Acceptance Criterion.
- [ ] Every Edge Case has a matching row in the Failure Mode Tests table.
- [ ] Every State Combination Matrix row has a corresponding test row.
- [ ] Every Branch Enumeration path is covered by either a happy-path or a Failure Mode Test.

### Terminology Hygiene

- [ ] Domain terms used in this spec are defined in the feature `README.md` glossary.
- [ ] Each domain term is used consistently — no synonyms slipping in mid-spec ("event" vs "session", "workspace" vs "project").
- [ ] Acronyms are spelled out on first use.

### Decision Traceability

- [ ] Every constraint cites either a discovery decision, an ADR, or a Project Principle from `templates/product-context.md`.
- [ ] Every `⚠️ Assumed` tag has a confirmed source after PM review, or is moved to the Risk Register.

If any item fails, the spec is **not ready for the Readiness Gate**. Fix the
prose and re-run the checklist before proceeding.

## Test Generation Brief — Agent Entry Point

**This section is where the implementing agent starts.** Not Overview. Not
Functional Requirements. Here. Read this section first, then follow the steps.

### Step 1: Verify readiness

Before writing any code, confirm all of these are present:

- [ ] Contract Definitions have real type names with `// Extends:` or `// Pattern:` references to real codebase files
- [ ] Test Boundary Map has a file path for every requirement
- [ ] Failing Tests section has executable code (imports, assertions), not comment skeletons
- [ ] Test Environment section has the exact runner command
- [ ] Codebase Context section has real file paths, not placeholders

If any are missing, STOP. Flag the gap and route the spec back to Step 6.

### Step 2: Create test files

For each file path in the Test Boundary Map:

1. Create the file at the specified path
2. Copy the executable test code from the Failing Tests section
3. Adjust imports to match the contract type names and file paths
4. Do NOT create any implementation files yet

### Step 3: Run tests and verify correct failures

Run the command from Test Environment.

Every test should fail. Verify the failure reason:

- **Correct:** missing module / function not defined → expected
- **Wrong:** SyntaxError, TypeError, or missing devDependency → fix the test first

### Step 4: Implement

1. Create the modules the test imports reference
2. Implement the minimum code to make each test pass
3. Run the test command after each meaningful change
4. When all tests pass, run the full suite to check for regressions
5. Refactor freely while tests stay green

### Step 5: Self-review

- [ ] All tests from Test Specification pass
- [ ] No tests were deleted or weakened to make implementation easier
- [ ] Failure Mode Tests all pass
- [ ] New code follows patterns cited in Codebase Context
- [ ] No new linter warnings introduced
```
